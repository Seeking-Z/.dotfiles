# Git 与改动隔离规范

本规范规定新任务开始前的版本交接、任务提交及改动隔离。报告与提交确认门槛适用于本仓库的所有任务和改动，不限于规范文件；所有 Git 操作仍须遵循已确认计划中的路径和操作范围。

## 新任务开始前：交接上一任务

- 使用上一任务报告中的提交标识和精确改动路径作为交接依据；不以宽泛的仓库扫描代替路径清单。
- 首次写入前，对交接路径检查 `git status`、暂存差异和未暂存差异。未跟踪文件不会出现在普通差异内容中，须结合限定路径的状态结果识别；只检查已获准的对象。
- 若已确认没有上一任务遗留改动，或上一任务报告明确记录无文件改动，则无需前置提交；仍须检查本任务计划中的精确目标路径。
- 若上一任务的改动已提交，核对提交标识和对应路径，不重复提交。若仍有上一任务的未提交改动，先审查精确差异；只有归属清楚且已确认计划包含前置提交时，才向用户报告来源任务、精确差异、拟提交路径和提交后核验方式，并在收到对该报告及范围的明确确认后独立提交。完成并核验前不得开始新任务写入。
- 用户已有改动一律视为保留内容；不要覆盖、重置、清理、暂存或纳入本任务。若它们与前置提交路径重叠、暂存内容归属不明，或无法区分上一任务与用户改动，暂停并请用户决定。
- 若有上一任务但没有报告，或无法确认路径或提交状态，暂停并请用户提供或确认精确路径及版本状态；不得用全仓库枚举代替，也不得自行推断哪些改动属于上一任务。
- 若 Git 不可用、当前目录不在可用仓库内，或无法检查历史和工作区状态，首次写入前暂停并报告；不得以暂存、备份或未核验的副本替代已确认的版本记录。

## 当前任务的提交与交接

- 计划须列明前置状态检查、必要的前置提交、拟提交精确路径、提交前完成报告与用户确认步骤，以及提交后核验。计划中确认允许提交只是必要条件，不替代完成报告后的再次确认；不需要提交时说明原因。
- 同一任务内的审查修正作为该任务的一组改动，不为每次编辑或局部修正单独提交。所有改动——包括创建、编辑、删除、移动、重命名及其他获准变更——均须纳入最终审查和完成报告；报告须列出全部任务改动，并单独列出拟纳入 Git 提交的精确文件路径。本节的“先报告、再确认、后提交”适用于所有本地提交，包括上一任务交接提交、当前任务最终提交和审查修正后的提交；每次提交都须对应最近一次报告中明确列出的内容与路径。有文件改动且确认计划包括提交时，只有除最终提交及其提交后核验外的计划步骤全部完成、提交前计划内验证通过或按计划判定为不适用、最终审查无待处理发现、待用户决定事项已解决，并明确判定任务内容完成后，才可向用户提交完成报告。收到用户对报告及其中精确提交范围的明确确认后，才可提交；此前的计划确认不代替该次确认。等待确认期间不得暂存或提交。用户提出疑问、建议、指出遗漏或要求修改报告时，不推定其已确认报告或提交；先按工作流程处理并重新报送。用户拒绝提交或确认范围有歧义时，停止提交并报告未提交路径和状态。无文件改动时说明无需提交。
- 提交前检查限定路径的状态、暂存与未暂存差异，并审查新建文件内容；对路径范围内的完整提交内容复核是否含无关改动、凭据、主机专属数据或本机生成内容，按 [`secrets-and-privacy.md`](secrets-and-privacy.md) 处理。
- 暂存只使用计划批准的精确文件路径；目录只有在计划明确授权相应子树时才能作为路径。不得使用 `git add .`、`git add -A`、通配符或 `git commit -a` 收集改动。删除或移动须在计划中分别列出源路径和目标路径，暂存时只操作已批准的精确路径，并同时核对 Git 识别的删除和新增路径。若需要部分暂存，必须在计划中说明并逐块审查；同一文件含用户改动或归属不明时暂停。
- 暂存后审查暂存差异，并确认目标路径没有尚未审查的未暂存改动。新增文件先按精确路径暂存。为避免把其他已暂存路径混入本次提交，使用 `git commit --only -- <精确路径>`；该操作忽略其他路径的暂存内容，但提交所列路径的当前工作区内容，因此提交前须确认其与已审查的暂存内容一致。其他路径的暂存内容应保持原状。路径含 Git pathspec 特殊字符时，确保按字面路径处理。
- 提交失败或钩子中止时，保留工作区和暂存区现场，不自动重试、重置或撤销暂存，不报告为已提交；记录错误和仍未提交的精确路径，按工作流程报告或提交修订计划。
- 提交前确认本地钩子的行为不会超出计划；若钩子可能运行未审查脚本或产生计划外影响，暂停并报备，不得绕过或禁用钩子。若提交签名会调用外部签名工具而计划未列明，暂停并请用户决定；不读取密钥或擅自关闭签名。提交使用本地 Git 作者/提交者元数据；不要为核对它而输出或汇报个人身份值，身份缺失或提交失败时停止，不自行修改 Git 身份配置。
- 提交后核对提交标识、纳入的精确路径和这些路径的状态，并在报告中记录提交标识、用途和文件清单。只报告获准范围内的状态；未检查全仓库时不得宣称整个工作区干净。
- 提交后核对通过时，向用户补报提交标识、实际纳入路径和核验结果，完成任务交接。
- 若提交后核验发现提交内容、路径范围或目标路径状态不符合已确认计划，不得报告任务完成；按工作流程重新打开任务，在已授权范围内修正并完成复审，再向用户提交修正完成报告，列明新的精确提交范围；收到用户明确确认后再建立修正提交。不得为修复而擅自改写既有历史。

## 改动隔离与其他 Git 操作

- 变基、分支切换、合并、推送、恢复、重置或清理都须单独列入已确认计划；本地提交不代表授权远程推送，也不代表授权改写历史。
- Git 历史可用于理解配置演变，但提交内容可能含敏感信息；查阅时遵守 [`secrets-and-privacy.md`](secrets-and-privacy.md)，不为版本审查而搜查凭据或主机专属数据。若差异意外显示疑似敏感值，停止提交和传播，不复述该值并请用户决定。
